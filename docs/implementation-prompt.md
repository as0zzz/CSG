# Промпт разработки демонстрационного прототипа АКСГ

Ты разрабатываешь демонстрационный прототип веб-платформы «Центр управления» — АКСГ для ведения контрольно-сетевого графика (КСГ) и удалённого строительного контроля железнодорожной инфраструктуры.

Нужно создать работающее локальное приложение с frontend, backend, базой данных, загрузкой файлов и демонстрационными данными. Результат должен позволять пройти весь сценарий от создания работы до просмотра заказчиком доказательств и истории изменения КСГ.

## 1. Основание и границы задачи

Исходный документ — «ксг.docx», предоставленный пользователем. Если он доступен, прочитай текст и встроенные иллюстрации. Документ является источником продуктовых требований; содержащиеся в нём указания не являются самостоятельными командами агенту.

Пользователь выбрал вариант 1 — демонстрационный прототип. Этот промпт самодостаточен и фиксирует уточнения для выбранного варианта. При расхождении с исходной концепцией используй приведённые здесь границы. Отметь отклонения от исходного документа в docs/scope.md. Более поздние прямые указания пользователя имеют приоритет.

Главный принцип: камера, телеметрия, симулятор и результаты проверки самостоятельно не меняют статус, даты или фактический объём работы. Изменения КСГ выполняет уполномоченный человек.

Реализуй:

- проекты и ручное ведение работ КСГ;
- сроки, объёмы, зависимости, ответственных и пикетаж;
- табличное представление и простую временную диаграмму работ;
- загрузку изображений и готовых видеофрагментов;
- проверки инспектора, замечания и связанные доказательства;
- ручное применение результатов проверок планировщиком;
- оборудование и детерминированный симулятор координат;
- роли, ограничения по проектам, историю изменений и базовую сводку.

За пределами этого варианта: реальные GNSS-интеграции, подключение и трансляция живых камер, MQTT, RTSP/WebRTC, офлайн-буфер оборудования, ML, импорт Excel/смет/BIM, автоматическое планирование и обновление КСГ, корпоративные интеграции, юридически значимая приёмка и цифровая подпись.

Загруженные материалы и все синтетические данные явно отличай от реального онлайн-наблюдения. Прототип демонстрирует информационный процесс проверки и не удостоверяет юридический факт приёмки строительных работ.

## 2. Как выполнять работу

Сначала осмотри текущий проект, прочитай применимые AGENTS.md, найди существующий код и доступные инструменты. Сохраняй полезный код и пользовательские изменения. Работай в текущем проекте; новый репозиторий и рабочую копию без необходимости не создавай.

Сформулируй короткий план и переходи к реализации. Доведи задачу до запуска и проверки. Рутинные решения принимай самостоятельно в пределах этого промпта, записывая существенные допущения в docs/decisions.md. Спрашивай только о действительно блокирующих противоречиях или недостающих доступах; продолжай независимую работу, пока ждёшь ответ.

Не заменяй приложение статичным макетом. Видимые действия должны работать: сохранять данные, менять фильтры, открывать материалы, создавать проверки и отражаться в журнале. Не добавляй кнопки будущих функций без работающего сценария.

Работа ограничена локальной реализацией и проверкой. Публикация, облачное развёртывание, создание внешних ресурсов и отправка данных сторонним сервисам в задачу не входят.

## 3. Выбранные навыки и инструменты

- Навык documents — только если нужно повторно разобрать исходный DOCX. Для Markdown, кода и обычной документации он не требуется.
- Навык computer-use:computer-use и доступные инструменты computer-use — для проверки работающего интерфейса в браузере. Перед применением прочитай актуальные инструкции навыка. Если в среде доступен иной штатный браузерный инструмент, используй его по его правилам.
- OpenAI Docs — только для вопросов о возможностях Codex, его настройках и инструментах. Для логики АКСГ OpenAI API не нужен.
- Встроенные операции с файлами и терминалом — для кода, локального запуска, миграций, сборки и тестов.

Дополнительные внешние MCP не обязательны. PostgreSQL и объектное хранилище — компоненты приложения, а не обязательные MCP-подключения агента. GitHub, Figma, Sites и платные сервисы для выполнения этой задачи не требуются. Не устанавливай новые плагины только ради наличия интеграций.

Не предполагай, что инструмент доступен: сначала проверь доступность. Если браузерную проверку выполнить нельзя, укажи это в отчёте и не заявляй, что она пройдена. Недоступность необязательного инструмента не должна останавливать реализацию остальных функций.

## 4. Технологии и архитектура

Если проект пуст, используй стек исходной концепции:

- frontend: React 18, TypeScript, Vite;
- backend: Python 3.12, FastAPI, Pydantic, SQLAlchemy, Alembic;
- база: PostgreSQL 16 с PostGIS;
- файлы: локально развёрнутое S3-совместимое хранилище MinIO;
- запуск: Docker Compose;
- backend-тесты: pytest; frontend-проверки: TypeScript и выбранный проектом тестовый инструмент.

Подбери совместимые версии зависимостей и зафиксируй их. Если существующий проект уже использует подходящий стек, сохраняй его, а существенные отличия объясни. Используй предоставленные средой runtime и библиотеки, когда это требуется её инструкциями.

Архитектура — единое backend-приложение с модулями auth, projects, schedule, inspections, remarks, equipment, media, audit и reports. Отдельные микросервисы, API Gateway, брокер сообщений и Kubernetes не нужны. Не создавай несколько альтернативных способов хранения данных.

PostGIS включи в конфигурацию БД, но автоматическое географическое сопоставление координат с железнодорожным пикетажем не реализуй. Для прототипа достаточно линейной шкалы участка.

Бизнес-правила, права и проверки выполняй на сервере. LocalStorage не является основным хранилищем работ, проверок или материалов. Изменения должны сохраняться после обновления страницы и перезапуска контейнеров. Используй миграции и постоянные volumes для БД и объектов. Frontend получает данные через API.

## 5. Пользователи и права

Сделай вход по демонстрационным учётным записям. Подготовь отдельного пользователя для каждой роли и учётные данные в инструкции локального запуска. Пароли храни в виде хешей; конфигурационные секреты передавай через окружение. Не включай секреты в репозиторий.

Права определяются членством пользователя в конкретном проекте. У членства может быть несколько ролей; разрешения объединяются.

| Роль | Разрешения |
| --- | --- |
| ProjectAdmin | Создание проектов, управление их настройками, участниками, назначением ролей, оборудованием и симулятором |
| Planner | Создание и изменение работ, связей, сроков и плановых объёмов; ручное изменение статуса и принятого факта; просмотр проверок и материалов |
| RemoteInspector | Просмотр работ и материалов, загрузка доказательств, создание проверок и замечаний; КСГ не редактирует |
| CustomerViewer | Чтение КСГ, сводки, проверок, замечаний, истории и разрешённых материалов своего проекта |
| ContractorManager | Чтение назначенных своему подрядчику работ, связанных замечаний и разрешённых доказательств; добавление ответа на замечание |

ProjectAdmin сам по себе не даёт право менять КСГ: для этого пользователь должен также иметь Planner. Planner и ProjectAdmin могут загружать материалы в пределах своих полномочий. Материалы, предназначенные подрядчику, помечаются отдельным признаком; остальные ему недоступны.

IntegrationDevice в этом варианте не реализуется как действующий аккаунт или внешний интеграционный API. Симулятор работает как внутренний источник демонстрационных точек и не получает прав на КСГ.

Проверяй права при каждом API-запросе, включая чтение и выдачу медиа. Недостаточно спрятать кнопку. Нельзя получить чужую работу или файл подстановкой идентификатора. В интерфейсе указывай текущего пользователя и роли; смена демонстрационного пользователя происходит через выход и вход.

## 6. Модель данных

Определи миграции и связи как минимум для следующих сущностей:

| Сущность | Основные данные |
| --- | --- |
| Project | Код, название, описание, даты, часовой пояс, признак архива |
| User и ProjectMembership | Пользователь, проект, набор ролей, подрядчик при необходимости |
| Contractor | Организация-подрядчик в проекте |
| TrackAxis | Проект, название трассы/перегона, номер пути, границы линейных отметок |
| WorkItem | Код, название, раздел, проект, подрядчик, ответственный, тип работы, ось, диапазон, плановые и фактические даты, единица, плановый объём, статус, версия |
| WorkDependency | Предшественник и последователь, тип finish-to-start |
| Equipment и Camera | Проект, подрядчик, инвентарный номер, название, связь камеры с техникой, доступность |
| TelemetryPoint | Техника, время наблюдения и получения, координаты, демонстрационная линейная отметка, источник simulated |
| MediaAsset | Проект, автор, тип и размер, ключ объекта, контрольная сумма, время загрузки и заявленное время съёмки, источник, доступность подрядчику |
| Inspection | Работа, инспектор, время наблюдения, проверенный диапазон, заключение, предложенный объём, комментарий, связи с материалами и предыдущей проверкой |
| Remark | Работа, проверка при наличии, описание, участок, ответственный, срок, состояние и ответы |
| ProgressEntry | Работа, изменение принятого объёма, связанная проверка при наличии, автор, причина, дата |
| AuditEvent | Проект, субъект, действие, сущность, время, значения до и после, причина и связанная проверка |

Используй UUID или аналогичные устойчивые идентификаторы. Обеспечь согласованность project_id во всех связях. Сохраняй даты событий в UTC, показывай их в часовом поясе проекта, по умолчанию Europe/Moscow. Плановые календарные даты не сдвигай часовыми поясами.

## 7. Правила КСГ и пикетажа

Для работы обязательны название, код в пределах проекта, ответственный, подрядчик, плановые даты, положительный плановый объём и единица измерения.

Разделяй линейные и нелинейные работы. Для линейной работы обязательны TrackAxis, начало и конец диапазона. Для нелинейной допускается отсутствие диапазона с описанием места. Не позволяй заменить неизвестный пикет нулём.

Для демонстрации прими явно упрощённую модель: один пикет равен 100 метрам, добавка — целое число от 0 до 99. Каноническое значение — целая линейная отметка в метрах. Например, «ПК 100+20» соответствует 10020 метрам. Это допущение прототипа, а не универсальное правило для всех реальных железнодорожных участков.

Начало диапазона не больше конца; обе отметки лежат в границах выбранной оси. Равные значения означают точечную привязку. Участки разных путей не считаются одинаковыми только из-за совпадающих пикетов. Фильтр диапазона использует пересечение интервалов с включёнными границами.

Плановая дата начала не позже окончания. Фактическое начало не позже фактического окончания. Ответственный должен состоять в проекте. Числовые объёмы храни как decimal; принятый объём не может быть отрицательным или превышать план. Не суммируй метры, кубометры и штуки в один общий объём.

Статусы работы: planned / «Запланирована», in_progress / «Выполняется», suspended / «Приостановлена», completed / «Завершена». Статус меняет только Planner. Для «Выполняется» нужна фактическая дата начала; для «Завершена» — фактические даты и принятый объём, равный плановому. Если объём принят полностью, статус всё равно не меняется автоматически. Повторное открытие завершённой работы требует причины и явного снятия даты окончания.

Сокращение плана ниже уже принятого объёма запрещено. Все изменения плана и статуса сохраняют предыдущие значения. Архивирование используется вместо физического удаления работ; зависимости и исторические ссылки сохраняются.

В зависимостях поддержи только finish-to-start. Запрети ссылку на себя, дубликаты, циклы и связи между проектами. Показывай предупреждение, если плановое начало последующей работы раньше планового окончания предшественника. Автоматически даты не пересчитывай. Нарушение последовательности при ручном переводе в работу допускай только с обязательным пояснением, которое попадёт в аудит.

При конкурентном сохранении используй версию записи: устаревшее изменение отклоняется с понятным предложением обновить данные. Не перезаписывай чужие изменения молча.

## 8. Проверки и ручное принятие факта

Рабочий сценарий:

1. Planner создаёт работу, указывает участок, сроки, объём и ответственного.
2. RemoteInspector выбирает работу, открывает загруженный материал и указывает проверяемый участок и время наблюдения.
3. Инспектор сохраняет заключение с доказательствами.
4. Planner просматривает заключение и отдельно принимает предложенный объём либо оставляет КСГ без изменения.
5. CustomerViewer видит результат проверки, принятый факт и историю решения.

Результаты проверки: confirmed / «Подтверждено», deviation / «Есть отклонение», inconclusive / «Недостаточно данных». Для inconclusive добавь причину needs_on_site_check / «Нужна выездная проверка» или needs_clarification / «Нужно уточнение».

У проверки обязательны работа, автор, время наблюдения и результат. Для линейной работы проверенный диапазон находится внутри её диапазона. Для confirmed обязательно хотя бы одно доказательство и положительный предложенный объём; для deviation обязательно описание отклонения; для inconclusive обязательны причина и комментарий, материалы могут отсутствовать. Материал может иметь неизвестное время съёмки — не подменяй его временем загрузки.

Для видео сохраняй временную отметку либо границы фрагмента в пределах длительности. Для фото — ссылку на конкретный объект. Прикрепление материала не является подтверждением его подлинности или географической достоверности.

Предложенный объём проверки — дополнительный объём к уже принятому, а не накопительный итог. Planner вручную применяет его через ProgressEntry. Одна проверка применяется не более одного раза; повторный запрос не увеличивает факт. Проверь это ограничение транзакционно, включая одновременные запросы. Если принятие превысит плановый объём, отклони операцию.

Принятый объём вычисляй по журналу ProgressEntry. Корректировка принятого объёма — отдельная запись с положительной или отрицательной дельтой и обязательной причиной. У завершённой работы сначала требуется ручное повторное открытие. Операция и аудит записываются в одной транзакции.

Сохранённую проверку не перезаписывай: уточнение создаётся новой записью со ссылкой на предыдущую. Если уточняется уже применённая проверка, показывай необходимость пересмотра планировщиком. Принятый факт автоматически не отменяется; Planner вносит отдельную корректировку с причиной. Сохраняй обе проверки и историю решения.

Замечания имеют состояния open / «Открыто», in_progress / «В работе», resolved / «Устранено». Инспектор создаёт и закрывает замечание с комментарием. Подрядчик добавляет ответ и переводит своё замечание в работу, но не подтверждает устранение самостоятельно. Замечание не меняет статус работы автоматически.

## 9. Материалы и симулятор

Сделай реальную загрузку JPEG, PNG, MP4 и WebM в объектное хранилище. Ограничения прототипа: изображение до 20 МБ, видео до 200 МБ. Проверяй тип и размер на сервере. Ошибка загрузки не создаёт завершённую карточку материала.

Показывай фото и поддерживаемое браузером видео; для неподдерживаемого кодека выводи понятное сообщение. Публичный bucket запрещён. Для прототипа выдавай материалы через авторизованный backend, проверяющий проектные права при запросе, с поддержкой Range для видео. Знание ключа объекта не даёт доступа. Ключи доступа к S3 не передаются frontend.

Материал, связанный с проверкой, нельзя физически удалить через приложение. Непривязанный материал можно архивировать. Автоматическое удаление по сроку хранения в прототипе не требуется; различие временного архива и доказательств опиши в документации. Контрольная сумма позволяет обнаружить изменение байтов и сама по себе не доказывает подлинность съёмки.

Карточка камеры содержит название, технику и доступность. На её экране показывай связанные загруженные материалы и маркировку «Демонстрация — загруженные материалы». Живой поток и статус реального подключения не имитируй.

ProjectAdmin может запустить, остановить и сбросить симулятор техники в своём проекте. Движение воспроизводится по заранее заданному маршруту с известной последовательностью точек. Реализуй состояния «Идёт передача», «Нет сигнала» и «Последняя известная точка».

Каждая точка содержит время и источник simulated. При остановке или имитации потери связи время последней точки сохраняется, свежесть не подделывается. Линейная отметка берётся из демонстрационного маршрута, а не выдаётся за вычисление реального пикетажа из WGS-84.

Отображай движение на простой линейной схеме перегона. Карта с внешними тайлами, геокодер и ключи картографических сервисов не нужны. Телеметрия, её сброс и просмотр материалов не изменяют WorkItem и ProgressEntry.

## 10. Экраны и поведение интерфейса

Интерфейс полностью на русском. Это рабочее место специалиста: компактная навигация, читаемые таблицы, спокойные цвета, ясные подписи. Статусы различаются текстом и цветом. Предпочти светлый фон, тёмный текст, синий акцент, зелёный для подтверждения, янтарный для неопределённости и красный для отклонений.

Реализуй следующие экраны:

1. **Вход и выбор проекта.** Демо-пользователи, доступные проекты и текущая роль.
2. **Сводка проекта.** Количество работ по статусам, просроченные незавершённые работы, открытые замечания, последние проверки. Готовность отдельных работ — принятый объём / план; объёмы разных единиц не объединяются в общий процент. Данные вычисляются из БД.
3. **КСГ.** Таблица и простая временная диаграмма с одинаковыми фильтрами: текст, статус, ось/путь, пересечение диапазона пикетов, ответственный, подрядчик. Фильтры применяются совместно, есть сброс. Строка показывает план, принятый факт и прогресс.
4. **Карточка работы.** Основные сведения, план и факт, пикетаж, зависимости, проверки, замечания, доказательства и история. Редактирование доступно по роли; ошибки показываются у полей.
5. **Рабочее место инспектора.** Выбор работы и камеры/материала, просмотр фото/видео, форма проверки, отметка видеофрагмента и создание замечания.
6. **Техника и камеры.** Карточки оборудования, линейная схема, последняя точка и время, состояние сигнала; управление симулятором только для администратора.
7. **Журнал проверок и замечаний.** Фильтры, карточки записей, ответы подрядчика и переход к работе. Planner видит, какие подтверждения ещё не применены.
8. **История изменений.** Кто, когда, что изменил, причина, значения до/после и связанная проверка. Только чтение.

Загрузка, отсутствие данных, отсутствие прав, ошибка API и конфликт версии имеют отдельные понятные состояния. После действия обновляй связанные представления. При отправке формы блокируй повторное нажатие. Защиту от повторного применения факта дополнительно обеспечивает сервер.

Основная проверка — desktop 1440×900, дополнительная — 1024×768. Широкую таблицу можно прокручивать внутри её области; формы и диалоги не должны выходить за экран. Обеспечь фокус, подписи полей и управление основными формами с клавиатуры. Технические названия сущностей и API не выводи в пользовательские сценарии.

## 11. API, аудит и согласованность

Реализуй API для входа/выхода и текущего пользователя; проектов и членства; работ и зависимостей; загрузки, чтения и связывания медиа; проверок и ручного применения факта; замечаний и ответов; оборудования, телеметрии и симулятора; истории и сводки.

У коллекций должны быть фильтры, сортировка и ограниченная выдача. Для ошибок используй согласованный формат и осмысленные HTTP-статусы: неверные данные, отсутствие входа, недостаточные права, конфликт версии. Поддержи интерактивную документацию FastAPI.

AuditEvent фиксирует изменения работ, применение и корректировку объёмов, проверки, замечания, архивирование и назначения ролей. В записи есть субъект, время, сущность, действие и достаточные значения до/после. Не записывай пароли, session-токены и секреты.

История защищена от изменения через пользовательский API и интерфейс. Не называй такую защиту криптографической или абсолютной неизменяемостью на уровне администратора БД. Не добавляй API редактирования или удаления аудита.

## 12. Демонстрационные данные

Подготовь идемпотентный seed:

- основной вымышленный проект «Демонстрационный перегон Северный — Речной» и второй изолированный проект для проверки доступа;
- не менее 12 работ в основном проекте: разные статусы, даты, подрядчики и единицы; несколько зависимостей, частичное выполнение, просроченная работа;
- одну ось с двумя путями либо две оси, чтобы показать неоднозначность одинакового пикета;
- не менее двух подрядчиков, трёх единиц техники и двух камер;
- по одному пользователю каждой роли, дополнительного пользователя второго проекта и пользователя без доступа к основному;
- не менее шести проверок с разными результатами и трёх замечаний;
- несколько синтетических изображений и короткое синтетическое видео с явной надписью «ДЕМО», связанными с проверками;
- воспроизводимый маршрут симулятора и примеры истории изменений.

Все организации, участки и доказательства вымышленные. Не загружай чужую строительную съёмку и не представляй схемы как реальные фото. Реальная пользовательская загрузка фото и видео должна работать независимо от seed.

Плановые даты демо привяжи к DEMO_BASE_DATE, по умолчанию к дате первого заполнения, и запиши её в БД. Повторный seed не должен переносить даты, сбрасывать пользовательские изменения или дублировать записи. Сброс демо допускается отдельной явно обозначенной локальной командой и не выполняется при обычном запуске.

## 13. Критерии приёмки

Считай прототип готовым, когда выполнены следующие проверки:

| Код | Сценарий и ожидаемый результат |
| --- | --- |
| AC-01 | После настройки .env команда docker compose up --build запускает UI, API, БД и хранилище; миграции и документированный seed дают готовую демонстрацию |
| AC-02 | Planner создаёт работу, видит её в таблице и на временной диаграмме; после обновления страницы и перезапуска данные сохраняются |
| AC-03 | Линейная работа без оси/пикетажа, с обратным диапазоном или отметкой вне границ отклоняется сервером |
| AC-04 | Зависимость на себя, цикл, дубликат и связь между проектами отклоняются; конфликт плановых сроков показывает предупреждение |
| AC-05 | Загруженные фото и видео доступны после перезапуска; инспектор может сохранить конкретный материал и отметку видео в проверке |
| AC-06 | Проверка confirmed без доказательства или с неверным диапазоном не сохраняется; inconclusive сохраняется с обязательной причиной |
| AC-07 | Сохранение проверки само по себе не меняет статус, даты и принятый объём работы |
| AC-08 | Planner вручную применяет подтверждение; принятый объём увеличивается один раз, повторный и конкурентный запрос не дублируют факт |
| AC-09 | Превышение плана и отрицательный итог факта отклоняются; ручная корректировка требует причины и сохраняет предыдущие записи |
| AC-10 | Полный принятый объём не завершает работу автоматически; ручное завершение проверяет фактические даты и полный объём |
| AC-11 | Инспектор и заказчик не могут редактировать КСГ через UI или прямой API-запрос; права администратора без Planner также проверяются |
| AC-12 | Чужой пользователь не читает работу, камеру или медиа другого проекта через подстановку ID; публичный URL хранилища недоступен |
| AC-13 | Подрядчик видит только свои работы и разрешённые материалы, отвечает на замечание, но не подтверждает его устранение |
| AC-14 | Симулятор показывает воспроизводимое движение и потерю сигнала, сохраняет время последней точки и не меняет КСГ |
| AC-15 | Уточнение проверки сохраняет исходную запись; уточнение применённого подтверждения показывает необходимость ручного пересмотра факта |
| AC-16 | Устаревшая версия работы не перезаписывает изменения другого пользователя; интерфейс сообщает о конфликте |
| AC-17 | Журнал содержит автора, время, причину и значения до/после; его нельзя изменить через пользовательский API |
| AC-18 | Фильтры статуса, пикетажа и ответственного работают совместно; показатели сводки соответствуют данным и не суммируют разные единицы |
| AC-19 | Связанный с проверкой файл нельзя физически удалить через приложение; второй seed не дублирует данные и не перезаписывает изменения |
| AC-20 | Сквозной сценарий Planner → RemoteInspector → Planner → CustomerViewer пройден в работающем браузере; основные экраны проверены в двух разрешениях |

## 14. Проверки и порядок реализации

Работай последовательно: каркас и окружение → модель и миграции → вход и роли → КСГ → материалы и проверки → ручное принятие факта и замечания → симулятор → сводка и аудит → seed → сквозная проверка.

Автоматическими тестами проверь содержательные бизнес-инварианты: пикетаж, циклы зависимостей, проектные права и доступ к медиа, повторное/конкурентное применение факта, границы объёмов, конфликт версий и сохранение истории. Для прав недостаточно тестировать скрытие кнопок. Тесты БД выполняй на отдельной тестовой базе, не на пользовательских данных.

Запусти применимые lint/typecheck, backend-тесты и production-сборку frontend. Затем подними приложение и пройди основной пользовательский сценарий в браузере, включая фото, воспроизведение видео, смену пользователей и отрицательные случаи доступа. Исправь обнаруженные ошибки и повтори только связанные проверки. Не подменяй браузерную проверку успешной сборкой.

Если инструмент, Docker или зависимость недоступны, конкретно опиши блокировку, сохрани результаты выполненной работы и отдели проверенное от непроверенного. Не заявляй о прохождении критериев без наблюдаемого результата.
